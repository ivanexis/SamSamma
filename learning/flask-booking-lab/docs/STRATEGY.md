# STRATEGY｜為何這樣做（雙軌策略）

> 給：你自己、合作社夥伴、面試官、Cursor  
> 一句話：**生產站維持 Cloudflare 丟檔＋Google 表單；學習站用 Flask／PG 證明紫生職能。**

---

## 1. 你現在的部署現實

| 項目 | 事實 |
|------|------|
| 官網上線 | Cloudflare **直接上傳靜態檔** |
| 預約／採購紀錄 | Google Forms → Sheets |
| B2C | 「即將開賣」（Pinkoi 待夥伴討論） |
| 人力／預算 | 低維運；理事長不寫程式 |

因此：**不適合**為了徵才，把合作社官網改成「一定要跑 Flask＋資料庫」才能預約。那會破壞現有營運與你的上線方式。

---

## 2. 為什麼還要做學習站？

紫生職缺明確需要：Flask／PostgreSQL／GCP、後台類維運、Git、測試、文件、**能說明為何改**、**會跟 AI 合作但仍負責結果**。

| 能力 | 只靠 Cloudflare 靜態站？ | 加學習站？ |
|------|-------------------------|------------|
| HTML/CSS/JS 小改版 | ✅ | ✅ |
| Forms 整合／文件 | ✅ | ✅ |
| Flask／Jinja2 | ❌ | ✅ |
| PostgreSQL／migration | ❌（Sheets≠SQL 履歷） | ✅ |
| GCP／查 log | ❌ | ✅（後期） |
| 後台列表／統計 | 🟡 Sheets 手查 | ✅ admin |

學習站的業務欄位**故意對齊**山莎蔓岸預約／採購，面試可講：

> 「客戶約束下生產用 Forms；我用同一資料模型做 Flask＋PG 學習站，證明進庫、後台與部署能力。」

## 3. 兩站對照（概念遷移）

| 合作社生產（軌 A） | 學習站（軌 B） |
|--------------------|----------------|
| HTML 表單 | Jinja2 表單 |
| POST Google formResponse | POST Flask route |
| Sheets 一列 | `bookings` / `inquiries` 一列 |
| 人工看表 | `/admin` 列表 |
| 筆數靠試算表 | SQL `COUNT` |
| Cloudflare 靜態 | 本機 → 之後 Cloud Run |
| 出錯 mailto fallback | Flask error handler + log |

---

## 4. 安全與主流 AI 開發姿勢（為何要文件化）

2024–2026 主流期望不是「AI 寫越多越好」，而是：

1. **任務邊界清楚**（任務卡）  
2. **人審 diff**（範圍／秘密／邏輯）  
3. **可驗證**（驗收清單）  
4. **可追溯**（Git Why＋Verify）  
5. **安全預設**（密鑰不進庫、參數化查詢、CSRF、最小權限）

這與紫生原文一致：AI 不取代工程師；不願善用 AI 的方式才會被取代——**善用＝收斂＋負責**，不是盲貼。

---

## 5. 製作順序（建議）

```
L0 本文件＋AGENTS＋提示協議（✅ 本批）
 → L1 本機 Flask 快樂路徑：表單→DB→admin 列表
   → L2 驗證／CSRF／SECURITY 對齊
     → L3 統計（count by plan/product）
       → L4 DEPLOY.md +（可選）GCP 試部署與查 log 紀錄
```

官網軌 A 繼續：P0-5 changelog、P1 結構拆分——與 L 並行時，**一次對話只做一軌一個任務 ID**。

另外我自己做一個練習用的報名後台（Flask），技術上對齊我應徵的工作，**不會強迫合作社改架構**。等以後真有會員／複雜後台需求，再評估要不要遷移。」
