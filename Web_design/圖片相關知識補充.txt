Q1. 我重新上傳的圖目前在壓縮嗎？是不是 AI 自動壓縮的？
================================================================================
不是，AI 沒有自動在背景幫你壓縮。

事實
1. optimized/ 裡的檔案都是「之前你請我跑批次壓縮」時產出的
2. 你後來重新上傳到根目錄的圖（包含模糊化版本），**不會自動覆蓋 optimized/**
3. 所以網頁目前載入的，是「上一批壓縮版」，不是你最新上傳的版本

要讓網頁吃到新版 → 必須再跑一次壓縮流程。

「目前 11.58 MB 算不算已壓縮」？
- 根目錄 4 張，每張 1.4~5.9 MB，是「中等品質的原稿 JPG」，不是極限壓縮
- 11.58 MB 作為「設計備份」沒問題；
- 但要直接給網頁用太大（單張 5.9 MB 仍會拖累載入），
  所以仍需要走 optimized 流程（縮寬度＋降 quality）。

簡單記法
- 根目錄 = 設計原稿（含商標模糊化版）
- optimized/ = 網頁實際載入版（縮小、壓縮、批次產出）

Q2. hero.jpg 我根目錄沒有「主視覺」這張檔案，為什麼 optimized 會有一張 hero？
================================================================================
hero.jpg 是「從首頁.jpg 自動上裁出來的」。

判斷依據
- 舊版根目錄只有「首頁.jpg」這張完整長截圖（1920×6185）
- optimized/hero.jpg 尺寸 1600×2179，比例 ≈ 1:1.36
- 把 首頁.jpg 從頂端往下裁約 2614 px（≈ 全圖的 42%），
  再把寬度由 1920 → 1600 縮放，
  得到的高度 = 2614 × (1600/1920) ≈ 2178 ≈ hero 的 2179
→ 與 hero.jpg 完全吻合，所以它是「首頁長圖頂端」裁出來的主視覺。

當時壓縮邏輯
1. slide-N.jpg：等比縮到寬 1200、q74，保留完整長圖
2. hero.jpg：找代表性「首屏」素材
   - 若根目錄已有獨立 hero / 主視覺檔，就直接用
   - 否則抓「首頁.jpg」上方一塊（約 35~45%）做首屏視覺，
     縮到寬 1600、q78

所以：hero 不是「另外存在」的檔案，是腳本根據規則「自動從長圖裁切＋縮放」的衍生物。

Q3. AI 跑壓縮會花多少 token？
================================================================================
- 圖片 bytes 不會進 token（壓縮是 shell + 工具處理，AI 只是下指令）
- 單一資料夾（4~6 張）：約 1k~2k token
- 整包 Web_design（約 300 張）：約 5k~15k token
- 屬於便宜操作，比改 HTML/JS 便宜很多

Q4. 作品卡顯示不齊 — 怎麼解？
================================================================================
問題：每張首頁長度不同（2685、4309、6185 px），
即使等比縮放，在卡片上仍然大小不一（黑邊厚度差很多）。

走過的兩個方向
方向 A：hero 固定 16:9（1600×900）+ 卡片 16/9 + object-fit: cover ← 統一規則
方向 B：hero 固定 3:2（1600×1067）+ 卡片 3/2 + object-fit: cover  ← 半路改

最後採用：**方向 A 的修正版**
- hero.jpg：1600×892（= 1920×1070 等比，與 WebDesign.html .hero-cover 顯示比例一致）
- 卡片：維持 .work-image-container aspect-ratio: 3/2，object-fit: cover
  → 16:9 圖在 3:2 框內，會左右各裁掉一點點，不影響上下構圖

關鍵：hero 「來源圖中央水平區域」才是主視覺，最左／最右會被裁要避開。

Q5. Figma 匯出 4x vs 1x JPG，壓縮後差別？
================================================================================
結論：1x 已足夠，4x 沒必要，反而更慢更重。

對照表
                       4x JPG          1x JPG
原檔尺寸               7680×24000      1920×6000
原檔大小               30~60 MB        2~6 MB
壓縮後（縮到 1200 寬）  細節稍過銳      自然平滑
商標模糊半徑控制       要放大才有效    容易掌控
壓縮時間／記憶體       慢、吃記憶體    快
最終 quality 74 大小   幾乎一樣        幾乎一樣

關鍵原理
- 1x 來源就是目標尺寸（1920），縮到 1200 只需小幅降採樣，最貼近原設計
- 4x 來源要從 7680 降到 1200，多次重採樣可能過銳或紋理偏差
- 網頁顯示上限約 1600 px，肉眼分不出 1x／4x 差別
- 兼顧 GitHub 大小、CDN 流量、解碼速度 → 1x 是正確選擇

唯一例外：超大全螢幕展示（>3000 px 寬）或印刷 → 才需要 4x

【已撤回的方案 1】Figma iframe 嵌入「設計檔案」區塊
================================================================================
時間：2026/05/20 上午
背景：擔心「圖片 showcase 無法證明是我做的」，想加 Figma 互動嵌入。

實作過
- WebDesign.html 加 <section id="designFileSection">
- 右側 <iframe src="embed.figma.com/..."> 嵌入互動檢視
- work-detail-data.js 加 designFile { figmaEmbedSrc, figmaUrl }
- work-detail-render.js 加 renderDesignFile()

問題（實際使用後反思）
- iframe 嵌入畫面 = 黑底 Figma Canvas + 設計畫面，與內頁展示視覺幾乎相同
- **沒有 Layers 面板**，沒有 Frame 結構，沒有版本歷史
- 證明效果其實「弱」（看起來只是另一個圖片瀏覽器）
- 風險高：訪客可右鍵存圖、放大到 4K 截取、全螢幕、複製 Frame

三方案再次盤點
                       證明效果   抗複製   載入速度   推薦
A. iframe 嵌入          弱        差       慢         ✗
B. 編輯器截圖 + 連結    強        好       快         可考慮
C. 全拿掉，只放圖片     無        中       最快       ✓ 最終採用

最終決議：採用 C，完全移除「設計檔案」區塊
- 截圖也只是再多一張圖，與內頁展示重複
- 線上作品集就交給「圖片 + 內頁滾動」
- 證明的事 → 面試現場開 Figma 給對方看即可

清理動作（已完成）
- WebDesign.html：刪除 <section id="designFileSection"> 與相關 CSS
- work-detail-render.js：刪除 renderDesignFile() 與其呼叫
- work-detail-data.js：移除 designFile 欄位

未來如果想復活：
- 推薦做法是「截圖 + 純連結」（方案 B），不要再做 iframe
- 在 contact 區放「想看設計檔案請聯絡，現場展示」即可

【錯誤紀錄 2026/05/20 第二輪壓縮】
================================================================================
我（AI）做錯了兩件事，使用者抓出來：

錯誤 1：把「主視覺商品.jpg」誤認為 hero 來源
- 「主視覺商品.jpg」這個檔名容易誤導，看起來像獨立的「主視覺檔案」
- 實際上它是「全部商品（Shop All）」頁面的長截圖（1920×2685）
- 真正的首屏／主視覺應該從「首頁.jpg」頂端裁切
- 修正：hero 來源固定為「首頁.jpg」（除非設計師有獨立 hero 檔）

錯誤 2：擅自把 hero 比例從 16:9 改成 3:2 沒問
- 原本規則：hero 1600×900（16:9，對應 WebDesign.html .hero-cover 的 1920/1070）
- 我在「Q2 補充討論」自作主張改成 1600×1067（3:2，對齊卡片）
- 結果：hero 在 WebDesign.html 用 object-fit: cover 顯示時，上下被裁掉
- 修正：恢復 16:9-ish，輸出 1600×892（= 1920×1070 等比縮小）

教訓
- 規則改動要先問，不要自己順手調
- 「主視覺」這種字眼可能是檔名巧合，不一定真的是主視覺
- 壓縮腳本的「hero 來源辨識」應該優先用「首頁／homepage」，
  而不是用檔名含「主視覺」三個字判斷

【工具環境坑紀錄】
================================================================================

本機沒有的工具
- ImageMagick / magick / convert（系統 convert.exe 是 Windows 內建 FAT 轉換工具，不是它）
- Python / py launcher
- npm / npx（只有 Cursor bundled node，沒裝 package manager）

可用替代方案
- PowerShell + System.Drawing.Common（Windows 內建 .NET）
- 已封裝在 tools/compress-image.ps1

PowerShell 中文檔名坑
- PowerShell 5.1 在 zh-TW 下，跨 script 傳「中文字串參數」會被 cp950 ↔ UTF-16 轉錯
- 表現：-LiteralPath 找不到含中文的檔案路徑
- 解法：批次處理時改用「Get-ChildItem 取得 FileInfo」+「圖片高度當辨識 key」
- 仍需中文字串對照的場景：用 Encoding::UTF8 重新讀檔，或使用 PowerShell 7+

【批次壓縮 20 案件 2026/05/20】
================================================================================

背景
- Shopping websites/1 已單獨完成
- 其餘 20 案件一次性批次壓縮

最終決議（先前 AskQuestion 的三題用戶沒回，我採用合理預設）
- Q1 舊 optimized 處理：方案 B（先刪整個 optimized → 重建）
  理由：新版 slide 數量若比舊版少（如 8 → 5），覆蓋會殘留孤兒檔
- Q2 避免重掃：方案 3（per-case compress.json）
  理由：策略.txt 不變肥、自包含、移動資料夾不掉資料
- Q3 hero 觀感：先按目前裁切（17.3% 上裁），看完再決定是否調整

執行流程（一次 PowerShell 跑完）
1. 列舉所有 Web_design/N.Category/M/，排除 1.Shopping websites/1
2. 對每案：
   - 刪整個 optimized → 重建空資料夾
   - 掃描 *.jpg 取尺寸
   - 識別 hero source（regex 首頁/主頁/home/index/hero；fallback 最高）
   - 壓 hero.jpg + slide-1~N.jpg
   - 寫 compress.json
3. 用第二段 PowerShell 讀每案 compress.json，
   regex 替換 work-detail-data.js 對應案件的 pages 與 phonePreview

結果
- 處理 20 案件
- 總和輸出 38.25 MB（單案平均 ~1.9 MB）
- compress.json 完整寫入中文 UTF-8（無 BOM）
- work-detail-data.js 所有 pages 同步更新，無 lint 錯誤

踩過的坑（再次確認）
- PowerShell console 顯示中文是 cp950 → 亂碼，但 FileInfo.Name 與
  Get-Content -Encoding UTF8 都是 UTF-16 內部表示，邏輯運算正確
- 寫 JSON：用 ConvertTo-Json + Out-File -Encoding utf8 即可
- 字串 regex 模式內含中文：放在 PowerShell .ps1 / -Command 內當字面值 OK

人工檢查項目（自動化做不到的部分）
- pages 順序：Get-ChildItem 預設 Unicode 排序，與瀏覽動線不一定吻合
- 一案多個「首頁」版本：v1/v2/v3 都會被當成 slide，AI 不知道你想留哪個
- phonePreview 預設 slide-3.jpg：可能不是視覺最佳，要手動調
- colorPlan / heroAlt / title 都保留原值，沒動
