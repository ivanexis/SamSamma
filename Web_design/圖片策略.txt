================================================================================
Web_design 圖片策略（SOP）
適用：所有 Web_design/N.Category/M/ 案件
最後更新：2026/05/20
================================================================================

【一句話總結】
- 根目錄 = 設計師交檔（語意命名、含原始長截圖）
- optimized/ = 網頁實際讀取（縮小、壓縮、固定命名）
- 兩者分開管理；根目錄有更新，optimized/ 一定要重跑


================================================================================
1. 資料夾結構
================================================================================

Web_design/
  └ N.Category/
      └ M/
          ├ 首頁.jpg            ← 設計原稿（語意命名）
          ├ 商品分類.jpg
          ├ 動物分類.jpg
          ├ 主視覺商品.jpg
          └ optimized/         ← 網頁實際讀取
              ├ hero.jpg       ← 統一檔名
              ├ slide-1.jpg
              ├ slide-2.jpg
              └ slide-N.jpg

說明
- 根目錄檔名：用中文／語意命名，方便人讀
- optimized/ 內檔名：必須是 hero.jpg 與 slide-1~N.jpg（程式依賴此規則）
- 圖片來源：每件 Figma 匯出 1x JPG 即可（不需 4x，差異肉眼分不出且更重）


================================================================================
2. Figma 端匯出規則
================================================================================

- 統一寬度：1920 px
- 高度：依頁面長度，不限制（首頁可能 6000+ px 長截圖）
- 格式：JPG（1x）
- 商標／敏感資訊：在 Figma 端先模糊化再匯出
- 主視覺：不需另存獨立檔案，hero 由「首頁」長截圖頂端自動裁出


================================================================================
3. 壓縮規則（產出 optimized/）
================================================================================

3-1. hero.jpg（作品集卡片 + 詳情頁主視覺）
- 來源：首頁.jpg（必選；如果未來有獨立主視覺檔，再用獨立檔）
- 動作：從來源圖「頂端」裁出一塊，再縮放
- 目標比例：1920 : 1070（與 WebDesign.html .hero-cover 顯示比例相同）
- 輸出尺寸：1600 × 892（= 1920×1070 等比縮小）
- 品質：JPEG quality 78
- 為什麼是「頂端裁切」：首屏視覺通常在頁面最上方（含 navbar、主圖、品牌色）

3-2. slide-N.jpg（內頁展示用，長截圖）
- 來源：根目錄所有 JPG（包含首頁本身）
- 動作：等比縮放至寬度 1200，不裁切（保留完整長度）
- 品質：JPEG quality 74
- 順序：依使用者瀏覽動線（首頁 → 列表 → 分類 → 內頁 → 結帳）

注意
- 首頁同時是「hero 來源」與「slide-1」── hero 是頂端裁切，slide-1 是完整全長
- hero 與 slide 是兩個獨立輸出，不要互相取代


================================================================================
4. 命名與順序規則
================================================================================

固定欄位
- hero.jpg                ← 作品集卡片 + 詳情頁主視覺
- slide-1.jpg ~ slide-N.jpg ← 內頁展示，依瀏覽動線

每件作品的 slide 順序建議
- 購物網站：首頁 → 全部商品 → 分類 → 內頁 → 購物車 → 結帳
- 形象網站：首頁 → 服務 → 案例 → 關於 → 聯絡
- 後台系統：登入 → Dashboard → 列表 → 編輯 → 設定

例外
- 一案同時有兩種風格 → 拆成 1-A / 1-B 兩個資料夾（不要塞在一筆作品內）


================================================================================
5. work-detail-data.js 對接欄位
================================================================================

每筆 'web-design-N-M' 至少要設這些欄位：

  basePath:     '../Web_design/N.Category/M/optimized'
  hero:         'hero.jpg'
  heroAlt:      '<簡述>'
  phonePreview: 'slide-X.jpg'   ← 選一張較短／適合手機呈現的 slide
  pages: [
    { label: '首頁',     image: 'slide-1.jpg' },
    { label: '全部商品', image: 'slide-2.jpg' },
    { label: '商品分類', image: 'slide-3.jpg' },
    ...
  ]

label 用中文，方便導覽列辨識。


================================================================================
6. 顯示端規則（已實作於 HTML/CSS，新案件不需動）
================================================================================

WebDesign.html（作品詳情頁）
- .hero-cover           aspect-ratio: 1920 / 1070；object-fit: cover
- .color-plan-section   aspect-ratio: 1920 / 807（依寬度縮放）
- .browser-frame        瀏覽器外框（macOS 三點 + 內含 showcase 滾動）
- showcase 行為         自動切換 4.5 秒、可手動翻頁、長截圖內部可垂直滾動

index.html（作品集卡片）
- .work-image-container aspect-ratio: 3/2；object-fit: cover
- 因為 hero.jpg 為 16:9-ish（1.794），3:2（1.5）卡片會略裁兩側
  → 設計時把主視覺主體留在「中央水平區域」即可，不要把重點放在最左／最右


================================================================================
7. 執行 SOP（每件新案件流程）
================================================================================

1. Figma 匯出 1920 寬、1x JPG（每個頁面一張）
2. 商標／敏感資訊在 Figma 端模糊化
3. 上傳到 Web_design/N.Category/M/ 根目錄（中文語意命名）
4. 跑壓縮：
   - 單案：「請壓縮 Web_design/N.Category/M」
   - 全部：「請壓縮所有 Web_design 案件」
   → AI 會自動處理 a~e 五個動作（見 §11）
5. 重新整理 index.html 與 WebDesign.html?id=... 驗收
6. 若 slide 順序不符合瀏覽動線 → 手動編輯 work-detail-data.js pages 陣列
   （label 取自原檔名，順序取自檔案列舉，需要時自行重排）


================================================================================
8. 壓縮工具與環境
================================================================================

本機可用工具：PowerShell + System.Drawing.Common（Windows 內建 .NET）
工具腳本：tools/compress-image.ps1
（本機沒裝 ImageMagick / Python / sharp；System.Drawing 已足夠）

AI 跑壓縮的成本參考
- 單一案件（4~6 張）：約 1k~2k token
- 整包 Web_design：約 5k~15k token
- 屬於便宜操作，比改 HTML/JS 便宜很多

注意（已踩過的坑）
- PowerShell 5.1 不能用「中文字串參數」跨 script 傳遞（cp950 ↔ UTF-16 會錯）
- 解法：壓縮腳本內用 Get-ChildItem 取得 FileInfo，**用圖片高度**辨識來源
- 高度衝突時：改用檔案大小 / 內容雜湊 / 互動詢問


================================================================================
9. 檢核標準
================================================================================

每件案件
- 根目錄總和 < 20 MB
- optimized/ 總和 < 5 MB
- hero.jpg：1600×892、< 250 KB
- slide-*.jpg：寬 1200、單張 < 700 KB（長截圖可放寬）

整包專案
- Web_design/ 整體（含所有作品）< 100 MB
- 不要把根目錄推到 GitHub（已列 .gitignore）
- 公開部署：FTP / R2 / 主機側補上 optimized/

11. 批次壓縮自動化（AI 跑壓縮的完整動作）
================================================================================

11-1. 五個動作（順序固定）
a. 清空 optimized/ 整個資料夾（方案 B 乾淨重來）
b. 掃描根目錄 *.jpg → 讀取尺寸（width × height）
c. 識別 hero 來源：
   - 第一優先：檔名 stem match 「首頁/主頁/home/index/hero」（regex）
   - Fallback：高度最大的那張（最長截圖通常是首頁）
d. 壓縮並寫入 optimized/：
   - hero.jpg：來源頂端裁切 → 1600×892（q78）
   - slide-1.jpg：hero 來源完整長截圖 → 寬 1200（q74）
   - slide-2~N.jpg：其餘檔案，依 Get-ChildItem 列舉順序（q74）
e. 寫 compress.json manifest 到案件根目錄

11-2. compress.json schema
{
  "case":        "1.Shopping websites/2",
  "scanned_at":  "2026-05-20",
  "hero_source": "首頁.jpg",
  "files": [
    { "src": "首頁.jpg",   "height": 6185, "outputs": ["hero", "slide-1"], "label": "首頁" },
    { "src": "內頁.jpg",   "height": 2424, "outputs": ["slide-2"],         "label": "內頁" },
    ...
  ]
}
- src      ：根目錄原檔名（含副檔名）
- height   ：原圖高度（用於下次重壓辨識，免重掃）
- outputs  ：對應到 optimized/ 的哪些輸出
- label    ：原檔名 stem，會自動寫進 work-detail-data.js pages[].label

11-3. work-detail-data.js 自動同步
- AI 壓縮完，會自動更新該案件的 pages 與 phonePreview
- 替換規則（regex 以 basePath 為錨）：
    pages 整個陣列 → 從 manifest.files 依序生成
    phonePreview   → 預設 slide-3.jpg（不足時退到 slide-2 / slide-1）
- 不會動到：basePath、hero、heroAlt、colorPlan、displayCategory、title、category
- 整個 file 用 UTF-8 寫回，不加 BOM

11-4. slide 順序的限制
- Get-ChildItem 預設按檔名 Unicode codepoint 排序
- 中文檔名排序結果不一定符合瀏覽動線（首頁 → 列表 → 內頁 → 結帳）
- 第一次壓完後請人工檢查 pages 順序，需要的話手動拖動 label/image 對應

11-5. 重壓策略（同案二次跑壓縮）
- 若 compress.json 已存在 → AI 可直接讀對應表，跳過尺寸掃描
- 來源檔換新版（如商標重新模糊）：壓縮腳本只認尺寸 hash 不認檔內容
  → 直接重跑就好，輸出名稱與 manifest 不變

11-6. 多個「首頁」版本（v1/v2）的處理
- 若根目錄有「首頁 1.jpg」「首頁 v2.jpg」「首頁.jpg」多個版本
- regex 會抓「第一個 stem 含首頁」的當 hero（通常是「首頁 1」或「首頁」）
- 其他版本變成 slide-N，label 保留原檔名（如「首頁 v2」「首頁」）
- 想指定哪一張當 hero → 改檔名讓「目標檔」排在最前面，或手動編 compress.json
