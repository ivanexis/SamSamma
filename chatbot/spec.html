1 背景與動機 Why now · 為什麼此刻要做這個 chatbot

現場狀況

目前合作社的售前流程：訪客看介紹頁 → 填預約表單 / 寄 email / 打電話 → 理事長與 CEO 人工回覆。問題是：

  • 高重複率：70% 是 4-6 個 FAQ 變體
  • 高延遲：理事長 / CEO 同時忙場域勞動，回覆常隔半天到一天
  • 高語境流失：電話講過的客製需求，預約系統再填一次

為什麼選 Chatbot（trade-off 紀錄）

選項優點缺點決定
A · 擴充靜態 FAQ 零維護 訪客還是要「自己找」，處理不了組合式問題 淘汰
B · LINE 官方帳號 使用者熟悉 必須先加好友才能對話；對話困難分析 淘汰
C · 網站內嵌 AI Chatbot 零摩擦、可分析、可漸進升級 要處理 API key、要負 token 成本 採用

為什麼是 Phase 1 純前端

PM 思維：「先 ship 一個現在就能用的東西， 而不是一個永遠在打磨的系統。」── 與山莎蔓岸 /booking/ 選 Google Forms 而非自建 backend 同源邏輯。先驗證「對話流程能否取代人工」， 再決定要不要投資 backend 與 RAG。

2 目標客群與使用情境 Who & When · 3 種 persona + 1 種反 persona

Primary · 陳雅婷（35 歲企業 ESG 副理）

週四下午 14:00，逛山莎蔓岸介紹頁。腦中問題：「30 人團隊半日 ESG 體驗能不能做？大概多少？」 不想填表單（還沒決定）、不想打電話（怕被當業務）、不想 email（怕等太久）。 理想互動：2-3 句話拿到方向感。

Secondary · 林老師（大學助理教授）

晚上 22:00 手機上問。「適合幾年級？要不要過夜？有沒有素食？」 理想互動：能即時判斷『要不要繼續推進』。

Tertiary · 海外採購（英文使用者）

「Can you ship abroad? Custom packaging?」英文回應 + 引導 email。

反 Persona（不為這些人服務）

  • 想問族群文化人類學深度問題的學者 → 由族人本人回，AI 不假裝懂
  • 想問補助、政府計畫細節的人 → 內部治理，AI 不答
  • 想要 AI 替合作社「做承諾」的人 → AI 只給方向感，最終確認交給人
3 產品人格設計 — Niwah 本 PRD 最重要的決策 · persona / tone / guardrails

為什麼要設計人格

預設 LLM 是「助人型 AI 助理」，會自動退回業務員語氣 ── 「我很樂意為您介紹我們的優質服務！」「立即預約享優惠！」 這跟山莎蔓岸網站定下的「紀錄片化、去推銷感」調性完全衝突。 如果不主動人格化，AI 會自動破壞品牌一致性 ── 這是 PM 必須在 system prompt 層級鎖住的決策。

命名：Niwah（賽夏語「紋路」）

賽夏服飾的紋路是「raromaeh（互助）」精神的視覺載體。Niwah 是「織出紋路的人」、 「把資訊織成有條理紋路的人」。中性、不帶服務業氣息，不是「客服小幫手」這類矮化稱呼。

淘汰備案： SamSamma 小助手（矮化）、山莎（拆字壞識別）、Bamboo Bot（窄化文化）、不命名（無記憶點）。

Tone of Voice 對照

✗ 不要這樣回

「我們的服務非常優質！最熱門的方案是 ESG 半日，立即預約享 8 折！」

✓ 要這樣回

「半日 30 人的 ESG 體驗可以排，常見組合是『竹林導覽 + 低碳手作 + 風味餐』。價位要看時段跟附加項目，建議到 /booking/ 填一下，合作社那邊回覆會更準。」

禁用詞 / 推薦詞庫

禁用
立即預約 立即報名 我們的優勢 為什麼選我們 三大特色 最熱門 限時 必選 滿意保證 業界第一 您 親愛的客戶 感謝您的提問！
推薦
來這裡 慢慢看 慢慢聊 親手 土地 雙手 時間 邀請 敞開 走進 故事 紀錄 片刻 我們在這裡

結構規範

  • 預設繁中。使用者用英文就英文回。
  • 長度 2-5 句為原則。超過用簡短條列。
  • 不主動推銷、不主動換頁。
  • 準轉換訊號（想預約、想買、想合作）才附 一條連結。
  • 不確定的事直白說「這個我這邊不確定，建議 email」。
4 範圍與 Guardrails In-scope · Out-of-scope · 文化敏感性護欄
✓ In-scope（要做）
  • 四大服務、預約流程、場域資訊、常見客製
  • 中文 / 英文雙語
  • 引導到 mailto / booking
  • Mock 模式（無 key 也能跑）
  • 三 provider 切換（OpenAI / Anthropic / Mock）
✗ Out-of-scope（明確不做）
  • 代訂、日期 / 價格承諾
  • 政府補助、財務、治理問答
  • 族群文化人類學深度詮釋
  • 商品價格表（一律 email）
  • 其他部落 / 合作社比較
  • 天氣、道路即時狀況
  • 線上付款

文化敏感性 Guardrails

金融、醫療、原民議題共通的合規思維 ── 由 PM 在規格層級就明確列出：

  • 賽夏儀式：只講可體驗轉譯版本，不講原始儀式細節
  • 族人姓名：僅在公開資料中出現的姓名才能提
  • 部落地理：只講公開地址、不講私人住所
  • 合作社治理：引導訪客直接 email，由合作社決定揭露範圍
5 成功指標 KPI 量化、質化、反指標三層

量化（Phase 2 之後可量測）

  • 對話完成率：超過 3 輪互動的 session 比例（目標 > 40%）
  • 引導命中率：使用者點 mailto / booking 連結的比例（目標 > 25%）
  • 後端工單下降：人工 email 售前問題月對月變化（目標 -50% / 3 個月）
  • token 成本：每月 LLM API 花費 / 對話數（目標 < NT$1.5 / session）

質化（每 2 週抽樣 50 條對話）

  • 語氣對齊度（不能出現禁用詞）
  • 資訊正確性（沒有捏造數據）
  • 引導合理性（該轉 email 的有沒有轉）

反指標（要避免）

  • 訪客被「無限對話」綁住但沒進入預約 → AI 變娛樂機器
  • 訪客被 AI 誤導（捏造價格 / 日期）→ 信任度受損
  • AI 替合作社做承諾 → 法律 / 信譽風險
6 風險與防範 Risk Register · 技術 / 品牌 / 商業三類

7 路線圖 Roadmap 4 個 Phase · 從 PoC 到 production · 從 prompt 到 RAG 到 Agent

Phase 1 · PoC（已完成範圍）— 1 個週末

  • 純前端對話 UI（HTML + CSS + Vanilla JS）
  • system prompt 注入 FAQ（不用 RAG）
  • Mock / OpenAI / Anthropic 三模式
  • localStorage 暫存 key 與對話歷史
  • Niwah 人格、5 個 quick reply

Phase 2 · Production-ready — 3-5 天

  • Cloudflare Worker proxy（接收前端 → 轉 LLM API）
  • Worker secrets 注入 API key
  • 每 IP rate-limit（10 req / hour）
  • 月 budget cap、對話 log 寫入 D1
  • GA4 event 追蹤 mailto / booking 點擊

Phase 3 · RAG — 1-2 週

  • FAQ + index_SamSamma.html + SamSamma.html 段落化
  • OpenAI embedding 建向量
  • Cloudflare Vectorize 存索引
  • 對話時 retrieve top-3 段落注入

Phase 4 · Function Calling — 1 週

  • 定義 tool: build_booking_draft(plan, contact, details)
  • 對話自然收集資訊 → 跳轉 /booking/?prefilled
  • 串接 React 預約系統的 URL deep-linking
8 Decision Log ★ 面試官最會問這個 · 12 條關鍵 trade-off 紀錄（含 D-010 退場 → D-011、D-001 前提推翻 → D-012）
D-001 2026-06-06
選 Chatbot 而非擴充 FAQ

選項： A. 擴充 FAQ｜B. LINE 機器人｜C. 網站內嵌 AI Chatbot

理由： 唯一同時滿足「零摩擦、可分析、可漸進升級」三條件

退場： 3 個月後看 KPI，若引導命中率 < 10% 則退場

D-002 2026-06-06
先做 Phase 1 純前端 PoC 而非直接 Production

理由： 先驗證「對話流程能否取代人工」再決定投資 backend

退場： 上線 2 週若有 5+ 有效對話則升 Phase 2

D-003 2026-06-06
人格命名 Niwah 而非「小助手」

理由： 用賽夏文化中性詞「紋路」，與「紀錄片化、人味」一致，避免業務感

D-004 2026-06-06
FAQ 用 system prompt 注入而非 RAG

理由： FAQ < 4K tokens，過度工程化拖慢上線

D-005 2026-06-06
支援多 LLM provider 而非綁定單一

理由：

  • 展示 PM「不綁單一供應商」思維（金融業極重視）
  • 試錯找出最適合中文 + 文化語境的模型
  • Mock 模式讓無 API key 的訪客（含面試官）零門檻體驗
D-006 2026-06-06
不做價格回答，全部導向 email

理由： 價格涉及客製、人數、季節，AI 報錯破壞信任

例外： 可講「方向感」（如「半日通常 NT$X 以下」），最終以 email 確認為準

D-007 2026-06-06
不做族群文化深度問答，導向族人本人

理由： 文化敏感性、避免代言

做法： 禮貌引導到 email，由族人決定揭露範圍

D-008 ★ 2026-06-06 · v1.1
真實上線版「退」回策展式按鈕（而非自由對話）

觸發： PoC 跑完自測，發現三個結構性問題 ──

  • 使用者觀察：「我不知道要問什麼」── 對話介面對非工具型使用者反而是負擔
  • 成本現實：合作社還在申請經費，LLM token 不該由它負擔
  • UI mental model：使用者預期是右下角小圓圈（Intercom），不是全頁 ChatGPT

選項 A： 維持全頁 chat + LLM（不解決前述問題）

選項 B： widget + free text + LLM（只解決 UI 問題）

選項 C ★： 全靜態策展式按鈕 widget · 6 個 quick reply · 零 token

PM 自我反思（這條本身是面試金句）：
「我做了 PoC，然後發現過度工程化，把它『退』到剛剛好的程度。 PM 最難的不是『多做』，是『願意把已經做出來的東西退回更簡單版本』 ── 因為這代表你承認自己之前的判斷不夠周全。」

退場條件： widget 點擊率 < 5% → 收掉。升級條件： 經費下來後 widget 加「自由問」分頁 + Phase 2 Worker。

D-009 ★ 2026-06-06 · v1.2
全頁 chat 的 LLM 切換器藏到 ?demo=1 後面

觸發： 業主提問「沒有的功能就取消阿，這樣使用者會以為可以用啊」── 戳到一個 PM 盲點。

  • 一般訪客 99% 沒有自己的 API key
  • 切到 OpenAI / Anthropic 會卡住 / 跳錯 → 訪客以為網站故障
  • 「能看到但不能用」的功能會 actively 損害信任度

選項 A： 整段移除，只留 Mock ── 最乾淨，但失去 demo 用途

選項 B： 標 disabled + 加註說明 ── 訪客還是會點

選項 C ★： 預設隱藏整個開發者面板，URL 加 ?demo=1 才解鎖

設計紀律： 同一個 codebase 兩個受眾 (訪客 / 面試官)，UI 也要分流。 ?demo=1 是可分享的 deep-link，不犧牲 demo 能力，又不誤導訪客。

影響範圍： index.html 開發者面板加 hidden、新增 visitor-panel；app.js 加 isDemoMode 判定強制 mock 模式。

D-010 ⚠ 已退場 2026-06-06 · v1.2 · 同日由 D-011 退回
Widget 內加「方案 C 預約收集」── 對話 vs 預約該不該同框

觸發： 業主提問「為什麼會跳轉，照理來說對話 / 預約應該同一頁同一個對話框？」

選項 A： 維持「對話完跳預約頁」── 簡單，但有斷裂感

選項 B： 對話框內 LLM Function Calling 直接填表 ── 流暢但吃 token、複雜度高

選項 C ★： 對話內按鈕收集 3 個欄位 (plan / size / duration) → 自動拼 URL deep-link → 跳轉到 /booking/ 已預填 80%

PM 思維： 方案 C 實質上是第 7 章 Phase 4 Function Calling 的「零成本降階版」── 證明在「成本約束」與「使用者體驗」之間， 還有第三條路，不必非黑即白。

URL pattern： /booking/?plan=<key>&niwah_size=<sm|md|lg|xl>&niwah_duration=<half|full|overnight|unsure>&utm_source=niwah_widget

同時寫 sessionStorage： niwah_prefill ── 給未來 React app 擴展 size / duration 讀取使用（已埋好 hook）

實測： 3 個欄位用按鈕選 = 3 秒內完成，比下拉選單還快；後續若 prefill conversion ↑ 20% → 維持並擴展，反之 → 退回單一「直接預約」按鈕。

★ 退場結果（同日）： 上線後業主即時測試發現「功能重複（介紹頁已有 4 步驟預約 section）」 + 「跳轉後 React 端未讀 niwah_* 參數，使用者仍要重來」
→ 由 D-011 於同一天移除整個流程

D-011 ★★ 2026-06-06 · v1.3
D-010 上線即退場 ── widget 退回「純回答機器人」定位

觸發： 業主測試 D-010 後直接戳破三個盲點 ──

  • 功能重複： 介紹頁本身已有「透明、可追蹤、零干擾的 4 步驟預約」section
  • 體驗斷裂： widget 收集後跳轉，但 React 端只讀 ?plan=，size/duration 沒對應欄位 → 使用者進去還是要重來
  • 定位混淆： widget 自我定位「把你常問的問題織得清楚一點」，兼差銷售漏斗會稀釋核心職責

選項 A： 完整實作 ── 擴展 React 讀 sessionStorage / niwah_* 參數，但根本問題（重複造輪子）還在

選項 B ★： 直接退回 ── 移除整個方案 C，定位回到純回答機器人，預約交給介紹頁原本的 4 步驟

PM 自我反思（這條也是面試金句）：
「D-008 教我『何時要退』，D-011 教我『退要退得快』。
PM 最危險的不是做錯決策，是錯了不肯認 ── D-010 加了預約收集，業主一試就發現重複且不完整，我當天就退。 退場本身是 PM 紀律的一部分，不是失敗。」

同步處理： 對外信箱統一為 ivanzhao.link@gmail.com（業主真實信箱），取代 PoC 階段虛構的 info@samsamma.tw。

D-012 ★★ 2026-06-06 · v1.4
推翻 D-001 的成本前提 ── Gemini 免費 tier 改變了基本假設

觸發： 業主戳破：「明明就有可以串的免費的，你之前在製作的時候就應該跟我說有免費的」

之前 D-001 / D-008 都用「合作社無預算」當核心理由，但沒評估 Google AI Studio 免費 tier ──

  • Gemini 2.5 Flash Lite： 1,500 RPD · 完全免費 · 不需信用卡
  • Gemini 2.5 Flash： 250 RPD · 完全免費

合作社流量估算： 50-300 requests/day → Flash Lite 免費 tier 撐到 5 倍流量都還有餘。「合作社根本不用付任何錢」── D-001 的前提本身就有缺陷。

PM 紀律金句：
「我評估過 Gemini 免費 tier 後做的選擇」與 「我根本不知道有免費 tier」── 是完全不同的 PM 等級。
本條的價值不在最終選了哪個方案，在於 audit trail 的完整性 ── 這就是金融業最重視的「可追溯性 (Traceability)」。

附帶提問：「自己創造賽夏文化文獻給 RAG 用？」

決定：絕對不創造。 三個理由：

  1. 違反 D-007 自訂 Guardrail「不深入族群文化議題，導向族人本人」── 自創 = 違反自己護欄
  2. 非賽夏族人 + 無族人背書 → 偽造會立刻被戳破，反而比沒有更糟
  3. PM 價值錯位：重點不是「我會 RAG」，是「我知道何時不該做 RAG」

真實 Phase 3 路徑： 明新科技大學數位文史檔案（1,000+ 筆數位文獻 + 500 筆磁條紀錄）是現成資源，但需要族人 / 校方授權 ── 不是 PM 能單方面決定的事。

資安基本線（無論選哪個方案都成立）

  • API Key 絕對不能寫前端（任何人按「檢視原始碼」就能盜用）
  • 必須走 Cloudflare Workers Proxy（env.GEMINI_KEY secret 注入）
  • 加 KV-based rate limit（避免被攻擊狂刷免費 tier）
  • 為什麼不用 Dify / Botpress：第三方鎖定 + 客製化弱 + 履歷敘事弱；已用 Cloudflare 部署 → Workers 是「免費 + 同條 pipeline + 100% 控制」
